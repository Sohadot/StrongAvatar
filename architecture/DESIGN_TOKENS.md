# Design Tokens Contract

## Purpose

Define the future visual token system for StrongAvatar.com before CSS, HTML templates, public content, or generated output exist.

## Construction State

Token-contract-only, no CSS exists yet, non-public, non-generative.

## Visual Doctrine

StrongAvatar.com must use a restrained institutional interface with a warm violet foundation, muted purple / plum spatial background, pale gold / amber illumination, cream-gold surfaces where needed, soft institutional glow, readable high-contrast text, controlled grid systems, reference-grade spacing, strong editorial hierarchy, and trust, governance, identity, and protocol aesthetics.

The visual system must not look like a cartoon avatar maker, childish gaming style, neon chaos, generic AI SaaS template, cheap affiliate website, dark cyberpunk dashboard, black-blue dominant interface, or hype-heavy startup surface.

## Visual Sovereignty

StrongAvatar.com must not imitate common AI SaaS, avatar-maker, gaming, cyberpunk, metaverse, or luxury-tech visual conventions.

The token system must create its own disciplined visual standard through a warm violet-gold identity field system that preserves authority, intelligence, spatial depth, reference trust, and institutional clarity.

Generic sites follow category conventions. Sovereign assets define category conventions.

The tokens should support a proprietary visual field rather than a generic design trend.

## Spatial Institutional UX

Spatial Institutional UX is the controlled design doctrine for a smart, modern, VR-inspired, spatially layered, protocol-driven, identity-field oriented, institutional, lightweight, SEO-safe, and accessibility-safe interface.

It is not dependent on actual VR hardware, WebXR, WebGL, heavy JavaScript, or immersive runtime. Spatial cues must remain informational, not theatrical.

## Identity Field Interface

The Identity Field Interface is the future visual metaphor for governed digital identity. It may use layered panels, subtle depth, controlled grids, protocol nodes, identity field lines, spatial card systems, score modules, governance warning surfaces, source and trust markers, buyer logic strips, and acquisition signal blocks.

It must not use cartoon avatar maker aesthetics, gaming toy interface patterns, childish metaverse visuals, neon chaos, VR headset gimmicks, generic AI SaaS gradients, hype-heavy startup visuals, heavy 3D scenes, animation-dependent comprehension, or decorative WebXR/WebGL before explicit approval.

## Violet-Gold Identity Field Interface

The Violet-Gold Identity Field Interface is the preferred visual metaphor. It uses warm violet, muted purple, plum spatial backgrounds, pale gold, amber light, cream-gold surfaces, protocol geometry, identity-field depth, and restrained institutional clarity.

It must feel invented, proprietary, spatial, institutional, and reference-grade rather than templated, borrowed, decorative, trend-driven, or dark cyberpunk.

## Color System

- `background_primary`: warm violet institutional foundation.
- `background_secondary`: muted purple / plum spatial field.
- `surface_primary`: cream-gold or softened institutional surface where needed.
- `surface_elevated`: restrained violet-gold raised surface for cards and modules.
- `text_primary`: high-contrast white or near-white text.
- `text_secondary`: silver or muted slate supporting text.
- `text_muted`: low-emphasis metadata and inactive context.
- `accent_primary`: pale gold identity-field illumination.
- `accent_secondary`: amber protocol or trust accent.
- `border_subtle`: quiet structural boundary.
- `border_active`: active focus or selected boundary.
- `warning`: restrained amber risk or governance warning signal.
- `trust`: warm gold positive trust or validated state signal.
- `source_note`: muted violet-gold source, citation, or evidence-state signal.
- `disabled`: unavailable, inactive, or non-public state signal.

## Typography System

- `display`: rare, high-authority page-level statement.
- `headline`: primary page or section headline.
- `section_title`: structured editorial section label.
- `body`: durable reading text.
- `small`: supporting compact text.
- `metadata`: review status, source notes, and registry details.
- `code_or_registry`: paths, slugs, registry keys, and protocol identifiers.

No font files or external font dependency are authorized yet.

## Spacing System

- `xs`: tight relationship between inline metadata.
- `sm`: compact grouping.
- `md`: default module spacing.
- `lg`: separation between major content units.
- `xl`: emphasis spacing for authority sections.
- `section`: page section rhythm.
- `page`: outer page margin and large viewport rhythm.

## Layout System

- Max content width must preserve long-form readability and institutional density.
- Grid behavior must support controlled editorial columns, protocol cards, link rails, and reference modules.
- Editorial rhythm must separate doctrine, evidence, links, and trust markers clearly.
- Protocol card layout must support dimension name, purpose, source status, and quality status.
- Reference page layout must support body content, source notes, internal links, and methodology context.
- Mobile-first constraints must preserve hierarchy without hiding governance or trust signals.
- Spatial layout must use layering and depth only to clarify identity, protocol, source, and governance relationships.

## Component Token Expectations

- `sovereign hero`: uses background, display, accent, and source-aware trust spacing.
- `thesis block`: uses headline, body, accent, and editorial spacing.
- `protocol dimension card`: uses surface, border, metadata, trust, and source-note tokens.
- `score module`: uses active border, warning, trust, and metadata states.
- `governance warning block`: uses warning, text, border, and source-note tokens.
- `source note`: uses source-note, metadata, and subtle border tokens.
- `internal link rail`: uses surface, muted text, border, and active states.
- `buyer logic strip`: uses secondary surface, metadata, and restrained accent tokens.
- `acquisition signal block`: uses trust, source-note, and non-promotional hierarchy tokens.
- `glossary card`: uses surface, section title, muted text, and controlled link tokens.
- `protocol nodes`: use accent, border, metadata, and trust tokens to show controlled relationships.
- `identity field lines`: use subtle border and source-note tokens to show relationship without visual noise.
- `spatial card systems`: use surface, elevated surface, section rhythm, and metadata tokens.

## Accessibility Requirements

Future tokens must support strong contrast, readable text, semantic hierarchy, keyboard-safe future components, no motion dependence, no animation-dependent comprehension, and no visual clutter.

## Performance Requirements

Future CSS must be lightweight. No unnecessary assets, decorative heavy scripts, WebXR, WebGL, immersive runtime, font-file sharing, or large image dependency are authorized.
